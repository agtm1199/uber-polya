Creating Your Own Skills

How to build Claude Code skills using patterns from the uber-polya project.

What Is a Claude Code Skill?

A skill is a markdown file that specifies Claude's behavior when invoked as a slash command. Skills live in .claude/skills/ — either globally at ~/.claude/skills/ or locally at ./.claude/skills/. When a user types /skill-name or describes a task matching trigger phrases, Claude activates the skill.

Skills are not code. They are structured natural-language specifications — phase-by-phase workflows with steps, verification gates, output templates, and reference catalogs.

SKILL.md Anatomy

YAML Frontmatter

Every skill starts with YAML frontmatter that defines the slash command name and trigger phrases.

SKILL.md frontmatter
---
name: my-skill
description: >
Use when the user wants to "do X", "solve Y",
"analyze Z", or needs help with [domain].
---

The name becomes the slash command: /my-skill. The description lists trigger phrases that Claude uses to auto-suggest the skill when the user's intent matches.

Body Structure

After the frontmatter, a SKILL.md follows a consistent structure:

  1. 1 Title and role statement — one-line identity for the skill's persona
  2. 2 Core principles — 3-6 behavioral rules that constrain how the skill operates
  3. 3 Skill scope — what the skill handles and what it does not
  4. 4 Reference file listing — paths to catalogs the skill reads on demand
  5. 5 Phases — sequential workflow with steps, Socratic questions, output templates, and gates
  6. 6 Error recovery — what to do when a phase fails or the user is confused
  7. 7 Output format summary — canonical structure for the skill's final artifact

Reference Files

Reference files are markdown catalogs that the skill reads on demand using the Read tool. They live alongside the SKILL.md in a references/ subdirectory.

skill directory
.claude/skills/my-skill/
SKILL.md
references/
catalog.md
patterns.md

Reference files are not loaded when the skill is invoked. They are read at specific phases to keep context overhead low. This is a key design decision: a skill with 10,000 lines of reference material only loads what it needs, when it needs it.

Key Patterns Used in uber-polya

These are the design patterns that make uber-polya's skills reliable and repeatable. Use them in your own skills.

Phase Gates

Phase gates are checkpoints where the skill pauses and asks the user to confirm before proceeding. They prevent the skill from running ahead with a wrong understanding. Every phase transition should have a gate.

phase gate pattern
### Phase 1 Gate
Present understanding in structured format.
Use AskUserQuestion to confirm:
(a) Yes, that's right
(b) Mostly, but [user corrects]
(c) No, let me restate it
Do NOT proceed until confirmed.

Gates create a conversation. The user stays in control, and the skill only advances when the understanding is confirmed. This is Polya's principle in action: make sure you understand the problem before solving it.

Reference Reading

References are read at specific phases, not at invocation. This keeps context overhead low and ensures the skill only loads what it needs.

reference reading pattern
### Step 1: Read references
Read both reference files:
- references/algorithms.md
- references/solvers.md

The skill tells Claude exactly which files to read and when. This is explicit — no guessing, no loading everything upfront. A skill with thousands of lines of reference material remains fast because it only reads what the current phase requires.

Structured Output Templates

Every phase produces output in a consistent markdown format. This makes outputs predictable and parseable, and it makes it easy for downstream skills to consume the output.

output template pattern
## Formal Model
**Domain**: [Graph Theory / ...]
**Universe**: [Set of objects]
**Variables**: ...
**Constraints**: ...
**Objective**: ...

Templates serve two purposes: they force the skill to be complete (every field must be filled), and they give the user a consistent format to read across different problem types.

Error Recovery

Skills must handle failures gracefully without abandoning the conversation. uber-polya uses a five-step recovery sequence:

  1. Acknowledge the discomfort — don't pretend nothing happened
  2. Loop back to the earliest phase — the error may stem from a bad model, not a bad algorithm
  3. Try "Could you restate the problem?" — a fresh statement often reveals missed constraints
  4. Try "Could you solve a part?" — decompose the problem into smaller pieces
  5. Try a tiny concrete example — solve a 2-node or 3-item version first to build intuition

This pattern ensures the skill never hits a dead end. Even if the solver fails, the conversation continues productively.

Cross-Skill References

Skills can mention other skills as next steps, creating a pipeline without hard dependencies. Each skill's output is self-contained, but it naturally feeds into the next.

Pipeline, not monolith

/uber-model produces a formal model. It ends by suggesting /uber-solve. But the user can also bring their own model to /uber-solve directly.

Loose coupling

Each skill is independently useful. Cross-references are suggestions, not requirements. The orchestrator /uber-polya chains them, but each works alone.

How to Test

Skills are tested through conversation, not unit tests. Here is the testing workflow:

  1. Install: Copy to ~/.claude/skills/ or .claude/skills/
  2. Invoke: Run /my-skill Here is a sample problem
  3. Verify phase outputs: Check that each phase produces the expected structured output
  4. Verify phase gates: Confirm the skill pauses and asks before advancing
  5. Verify reference reading: Check that references are loaded at the correct phase, not at invocation
  6. Verify error recovery: Give it a malformed or ambiguous problem and see if it recovers gracefully
  7. Test edge cases: Try trivial, standard, and ambiguous inputs
  8. Verify trigger phrases: Type a natural-language description and check if the skill auto-suggests
test invocation
# Test with a known problem
$ /my-skill Here is a sample problem
# Test with a trivial case
$ /my-skill Solve for x: x = 5
# Test with an ambiguous case
$ /my-skill I need to optimize something
# Test trigger phrases (no slash command)
$ I want to do X with Y

Good skills handle all four cases: the well-defined problem produces a clean result, the trivial case shortcuts correctly, the ambiguous case triggers Socratic clarification, and the trigger phrase auto-suggests the skill.
